# 주차장 데이터 결합 평가 (2026-08-04)

`parking_*` 테이블을 충전기 가용성 예측에 결합할 가치가 있는지, 그리고 UI 표시용
정보로는 어느 정도 쓸모가 있는지 평가한 기록.

**결론**

- **원래 가설("주차장 상태가 충전소 가용성에 영향을 준다")은 기각.**
  시간대 효과를 걷어낸 잔차 상관 −0.073(R² 0.54%).
- **기각 근거는 표본 부족이 아니다.** 매칭된 130곳은 거리 중앙값 40m 에 이름까지
  일치하는 *같은 부지 안 충전기* 다. 가설이 맞다면 **거기서 가장 강하게** 나왔어야
  하는데 안 나왔다. "적어서 못 봤다" 가 아니라 "최선의 조건에서 봤는데 없었다" 다.
- **UI 표시용으로는 유의미.** 다만 커버리지가 지역별 0~29%로 심하게 편중돼 있다.

### 왜 안 통했나 (물리적 설명)

- **충전 구획은 대개 전용이다.** 주차장이 만차여도 EV 자리는 비워 둔다. 점유율
  100% 인데 충전기는 비어 있을 수 있고 그 반대도 성립한다.
- **수요의 성격이 다르다.** 주차는 방문객 체류(수 시간), 충전은 세션(30~60분)에
  묶인다. 둘 다 낮에 붐비지만 그 공통분모는 이미 `hour`/`minute_slot` 이 잡는다.
  그 위에 남는 증분이 없었다.

이 기각은 커버리지가 늘어도 뒤집히기 어렵다. 신호가 희석된 게 아니라 메커니즘이
다르기 때문이다.

---

## 0. 먼저 — 지금 parking 코드는 죽어 있다

`recommend_api/parking.py` 가 조인하는 **`ev_charger_parking_map` 테이블이 존재하지
않는다.** 그래서 `load_latest_occupancy_for_stations()` 가 항상 빈 결과를 돌려주고,
추천 응답의 `parking_occupancy_coefficient` 는 늘 기본값 `1.0` 이다.

에러가 나지 않아 겉으로는 정상으로 보인다. **현재 parking 데이터는 우리 서빙에서
한 바이트도 쓰이지 않는다.**

---

## 1. 세 관문

결합 가치는 커버리지 → 시간해상도 → 신호 순으로 검증했다. 하나라도 무너지면
나머지는 볼 필요가 없다.

### 관문 2 (시간 해상도) — 통과

```
수집 주기      10분, 109곳 전량, 끊김 없음
보유 기간      2026-07-23 ~ 현재 (우리 status 와 거의 동일)
요청 시점 나이  0~10분
```

예측 horizon 5~60분에 충분하다.

### 관문 1 (커버리지) — 여기서 막힌다

```
parking_lot_info 등록 주차장          1,767곳
그중 실시간 상태가 들어오는 곳          109곳   (6%)
충전소 4,157곳 중 100m 이내             136곳   (3.3%)
급속 652곳 중 100m 이내                  67곳   (10.3%)
```

300m 로 넓히면 14.8% 가 되지만, 그 거리의 주차장 점유율이 해당 충전기 접근성과
관계있다고 보기 어렵다.

### 관문 3 (신호) — 없다

**주의: 원시 상관을 믿으면 안 된다.** 주차 점유율과 충전기 가용률은 둘 다 하루
리듬을 따르는데, 우리 모델은 이미 `hour`·`minute_slot` 을 쓴다. 따라서 시간대
평균을 제거한 **잔차끼리** 봐야 "얹었을 때 남는 증분"이 나온다.

100m 이내 매칭 130개 충전소, 64,570행(30분 격자, 12일):

| 지표 | 값 |
|---|---|
| 원시 상관 | r = −0.069 |
| **시간대 제거 후 잔차 상관** | **r = −0.073 (R² 0.54%)** |
| 충전소별 잔차 상관 중앙값 | r = −0.027 |
| (비교) 1시간 전 자기 가용률 | **r = +0.704** |

모델이 이미 쓰는 `avail_ratio_60m` 계열 신호와 자릿수가 다르다.

`config.py` 의 세션 prior 기각 사례와 같은 결말이 예상된다 — AUC 는 미세하게
오르고 사용불가 recall·캘리브레이션은 나빠지는 교환.

## 2. 그런데 표시용 정보로서는 다르다

정확도와 무관하게 **사용자에게 유용한가**는 별개 질문이다. 아래 넷으로 봤다.

### 데이터 품질 — 살아 있다

```
실시간 주차장 109곳 중 값이 고정된 곳     5곳 (5%)
점유율 변동폭(max−min) 중앙값             58.4%p
40%p 이상 변동하는 곳                     79곳 (72%)
```

죽은 센서가 5% 뿐이고 대부분 실제로 크게 변한다.

### 정보량 — 만차가 실제로 발생한다

```
전체 관측 점유율   평균 40.6%  중앙값 32.4%
70% 이상            21.6% 의 관측
80% 이상            15.6%
90% 이상            10.7%
95% 이상             7.8%
한 번이라도 90% 넘은 주차장   54곳 / 109곳 (50%)
```

**추천된 충전소 10곳 중 1곳꼴로 주차장이 거의 찬 상태**라는 뜻이다. 이때 경고를
띄우면 헛걸음을 막을 수 있다.

### 매칭 품질 — "가까운" 게 아니라 "같은 장소"다

100m 이내로 매칭된 급속 충전소의 실제 거리:

```
시설공단대구_서변1 공영주차장    0.45m
범어공영주차장                   0.78m
상인공영주차장                   1.14m
월촌공영주차장                   1.45m
대구시_월촌공원주차장            1.52m
칠성공영주차장                   5.95m
```

거리가 **1m 안팎**이고 충전소 이름 자체가 공영주차장이다. 우연히 가까운 게 아니라
**주차장 부지 안에 설치된 충전기**다. 그래서 주차장 점유율은 "충전기까지 진입할 수
있는가"를 직접 알려준다.

모델 신호가 없는데 표시 가치는 있는 이유가 여기 있다. **충전기가 비어 있어도
주차장이 만차면 못 들어간다.** 이건 예측 정확도로는 안 잡히지만 실제 낭패다.

### 요청 관점 커버리지 — 지역 편중이 심하다

대구 주요 지점 반경 2km 급속 충전소 중 주차 정보 보유 비율:

| 지점 | 반경 2km 급속 | 100m 매칭 | 300m 매칭 |
|---|---|---|---|
| 동성로(중구) | 33곳 | 5곳 (15.2%) | 13곳 (39.4%) |
| 수성구청 | 28곳 | 4곳 (14.3%) | 9곳 (32.1%) |
| 성서산업단지 | 14곳 | 4곳 (28.6%) | 5곳 (35.7%) |
| 동대구역 | 37곳 | 4곳 (10.8%) | 11곳 (29.7%) |
| **칠곡(북구)** | 13곳 | **0곳 (0%)** | **0곳 (0%)** |

top-10 추천이면 보통 1~3곳에 주차 정보가 붙고, 칠곡처럼 아예 없는 지역도 있다.

## 3. 권고

### 지금 하지 말 것

**모델 피처 결합.** 커버리지 3~10% 에 증분 R² 0.54% 다. 결측을 0 으로 채우면 모델이
"주차 정보 있음" 을 충전소 ID 처럼 외운다.

### 할 만한 것

**`ev_charger_parking_map` 을 만들어 표시용으로만 쓴다.** 좌표 기반 100m 매칭으로
136쌍이 나온다. 응답의 `station.parking` 필드는 이미 `service.py:485` 에 구현돼
있으므로, 매핑 테이블만 채우면 코드 수정 없이 살아난다.

UI 는 "있으면 보여주고 없으면 숨기는" 형태여야 한다. 커버리지가 지역별 0~29% 라
필수 정보로 다루면 안 된다. 특히 **90% 이상일 때 경고**가 가장 값이 크다(관측의
10.7%).

### 다시 볼 조건

실시간 주차장이 109곳 → 500곳 이상으로 늘면 관문 1·3 을 재검토할 만하다. 지금은
표본이 130 충전소뿐이라 "신호 없음" 결론 자체의 신뢰도도 높지 않다.

## 4. 용량 관점

우리 코드가 **한 번도 참조하지 않는** parking 테이블:

```
parking_api_raw          421.6 MB   (1,417행 — 행당 300KB 원본 JSON)
parking_realtime_area    215.0 MB   (121만행)
parking_realtime_zone     23.6 MB
parking_realtime_floor     4.5 MB
parking_lot_zone           1.4 MB
parking_lot_theme          0.1 MB
                       ─────────
                        약 666 MB   ← 전체 DB 1,373MB 의 절반
```

우리가 쓸 가능성이 있는 건 `parking_realtime_status`(301MB) 와
`parking_lot_info`(4.8MB) 뿐이다.

수집기는 `~/parking-collector/`(호스트 crontab, 10분 주기)이며 **이 저장소 소유자
본인 것**이다. 초기에 팀원 것으로 오인했으나 서버·crontab·디렉터리 모두 본인 계정이다.

512MB 버퍼 풀을 EV 파이프라인과 공유하므로 실제 비용이 있다 — 2026-08-04 부하
테스트에서 `parking_api_raw` 의 BLOB 컬럼 하나가 32초 만에 버퍼 풀을 75%→97% 로
밀어올려 `ev_charger_status` 인덱스 페이지를 밀어냈다.

### 적용한 보존 정책 (2026-08-04)

`scripts/etl/prune_parking.py` + compose `parking-prune` 서비스(24시간 주기).
그 전까지 parking 계열에는 **보존 정책이 하나도 없었다**.

| 테이블 | 보존 | 근거 |
|---|---|---|
| `parking_api_raw` | 7일 | `normalize_latest_parking_realtime()` 이 최신 1건만 읽음 |
| `parking_realtime_status` | 45일 | 추천 API 표시용. EV 롤링과 창을 맞춤 |
| `parking_realtime_area/zone/floor` | 7일 | 우리 코드가 참조하지 않음 |
| `parking_lot_info` | 무제한 | 1,767행 고정, 매핑 생성용 |

```
전   971 MB / 105 MB일 무한 증가  → 1년 37.5GB
후   약 1.8 GB 에서 안정
```

표시 기능까지 뺄 거라면 `--status-days 7` 로 낮추면 parking 전체가 400MB 아래로
내려간다. 매핑 테이블과 `parking.py` 는 그대로 둬도 무해하므로 나중에 되살릴 수 있다.

## 재현

**순서대로** 실행할 것. `parking_eval.py` 가 좌표 매칭 결과를
`data/reports/_parking_match.pkl` 로 떨어뜨리고 나머지 둘이 그걸 읽는다.

```bash
py scripts/analysis/parking_eval.py      # 커버리지·신선도 (+ 매칭 pkl 생성)
py scripts/analysis/parking_signal.py    # 잔차 상관 (관문 3)
py scripts/analysis/parking_utility.py   # 표시용 가치
```

Windows 에서는 한글 출력이 cp949 로 깨지므로 `PYTHONIOENCODING=utf-8` 을 붙인다.
