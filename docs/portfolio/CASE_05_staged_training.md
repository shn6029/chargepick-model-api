# 케이스 스터디 5 — RAM에 안 들어가는 학습을 디스크로 옮기기

> **한 줄**: 학습 데이터가 RAM을 넘어서 단계 적재 경로를 만들었다.
> 디스크를 아끼려고 `float32`를 골랐더니 **피크 메모리가 오히려 두 배**가 됐고,
> 그 원인이 sklearn 내부의 dtype 검사였다.

| | |
|---|---|
| 기간 | 2026-08-10 (경로 신설) · 2026-08-18 (float64 전환) |
| 문제 | 설계행렬 14,498,475 × 105 = **12.18GB**, 총 RAM 15.6GB 머신 |
| 결과 | 피크 RAM **23GB → 11GB** (디스크 6.09 → 12.18GB를 대가로) |
| 보장 | 정본 경로와 **예측이 동일**함을 테스트로 검증 |
| 근거 | [staged_training.py](../../recommend_api/staged_training.py) 독스트링 |

---

## 1. 문제 — 데이터가 늘어 RAM을 넘었다

정본 학습 경로는 `build_horizon_dataset(df, HORIZONS)`로 **7개 지평을 한 번에 전개**한다.
base 행 하나가 ETA 5·10·15·20·30·45·60분 샘플 7개로 불어난다.

2026-08-10 시점 실측 외삽으로 **약 21.5GB**가 필요했다(3지평 × 810k 행에서 4.94GB).
총 RAM 15.6GB 머신에서는 물리적으로 안 들어간다.

그런데 진짜 문제는 그게 아니었다.

> `prune_status.py --days 45`로 보존이 45일인데, 그 시점 데이터는 **19일치**였다.
> 45일이 차면 base 행이 약 2.4배가 되어 **50GB대**가 된다.

**"RAM 큰 머신을 쓰면 된다"로 피할 수 있는 문제가 아니었다.** 데이터가 정책상
계속 늘도록 설계돼 있으므로, 메모리에 비례하지 않는 경로가 필요했다.

---

## 2. 설계 — 디스크를 세 번 경유한다

```
DB
 └→ ① parts (parquet, 청크 단위)          수십 MB × N
     └→ ② 정확 중앙값 · 더미 수준          열 단위 스캔
         └→ ③ 설계행렬 memmap             12.18GB (디스크)
             └→ HGB.fit(memmap)           제로카피
```

핵심은 **parquet이 컬럼 저장**이라는 점이다. 중앙값을 구할 때 전체를 올릴 필요 없이
**한 열씩** 읽으면 열당 수십 MB로 싸다. 그래서 표본 근사가 아니라 **정확값**을 쓸 수 있었다.
더미 컬럼의 중앙값은 1의 비율에서 바로 유도한다.

마지막 memmap은 디스크에 있는 파일이지만 numpy 배열처럼 다뤄지고,
**sklearn이 페이지 단위로 읽어간다** — 조건이 맞으면.

그 "조건"이 4절의 주제다.

---

## 3. 가장 어려웠던 것 — "같은 모델"을 보장하기

저메모리 경로가 정본과 **다른 모델**을 내면 아무 의미가 없다.
등가를 깨뜨리는 요인이 네 가지 있었고, 넷 다 맞춰야 했다.

### ① 행 순서 — 이게 제일 무서웠다

HGB의 `_BinMapper`는 구간 경계를 정할 때 **20만 행을 표본추출**한다(`subsample=200_000`).

> **행 순서가 바뀌면 뽑히는 행이 달라지고, 경계가 달라지고, 다른 모델이 나온다.**

실측으로 **같은 데이터를 순서만 섞어** 적합했더니 예측이 최대 **0.086** 벌어졌다.
확률을 그대로 점수에 싣는 시스템에서 0.086은 큰 값이다.

그래서 지평 블록을 `HORIZONS` 순서로 이어 붙여 `build_horizon_dataset`의
출력 순서를 그대로 재현했다.

### ② 더미 — UNK 수준을 빠뜨리면 열이 어긋난다

정본은 `fillna("UNK")` 후 `get_dummies`한다. 청크로 나눠 읽으면 어떤 청크에는
`UNK`가 없을 수 있고, 그러면 열 개수가 달라진다. 수준 집합을 먼저 전량 스캔해
확정하고, 열 순서도 `get_dummies`의 사전순을 따랐다.

### ③ 중앙값 — 표본 근사를 쓰지 않았다

2절의 컬럼 저장 덕분에 정확값을 감당할 수 있었다. 근사를 썼다면
결측 대체값이 달라져 등가가 깨진다.

### ④ dtype — 값이 같음을 논증했다

parts를 내릴 때 이미 float64 컬럼을 float32로 낮췄으므로, memmap을 float64로
넓혀도 **되살아나는 정밀도는 없다.** 차이가 날 수 있는 건 중앙값 대체값과
2²⁴를 넘는 정수뿐인데, 전자는 255분위 구간 경계에 묻히고 **후자는 이 피처 집합에 존재하지 않는다.**

### 검증 — DB 없이 예측 동일성까지

`test_staged_equivalence.py`가 합성 horizon 프레임을 만들어 두 경로에 똑같이 태운다.

| 검사 | |
|---|---|
| 1 | `feature_columns`가 같은가 — 이름·개수·**순서** |
| 2 | `medians`가 같은가 — 더미 포함 104개 전부 |
| 3 | 결측을 메운 뒤 행렬 값이 같은가 |
| 4 | 같은 하이퍼파라미터로 적합했을 때 **예측이 같은가** |

**4번이 본질이다.** ①의 `_BinMapper` 문제 때문에 3번까지 통과해도 4번이 깨질 수 있다.

## 4. 반직관적 발견 — `float32`가 메모리를 **더** 쓴다

memmap을 처음엔 `float32`로 만들었다. 디스크가 절반이니 당연한 선택으로 보였다.

그런데 적합 중에 시스템이 죽기 직전까지 갔다. 프로세스 private가 **22.9GB**였고,
시스템 커밋이 **40.89GB / 한도 41.85GB**까지 차서 **가용 RAM이 36MB**로 떨어졌다.

원인은 sklearn 1.9.0 HGB 내부에 있었다.

```python
check_array(X, dtype=[X_DTYPE])   # X_DTYPE == np.float64
```

**float32를 넘기면 RAM에 float64로 통째 복사한다.** 직접 재봤다.

| 입력 memmap | 출력 dtype | memmap 유지 | 메모리 공유 |
|---|---|---|---|
| float32 | float64 | ✗ | ✗ **전량 복사** |
| **float64** | float64 | ✓ | ✓ **제로카피** |

float64 memmap은 `np.asarray`가 **뷰**를 돌려주므로 파일 기반으로 남고,
비닝이 디스크에서 페이지 단위로 읽는다.

2026-08-18 재학습(14,498,475 × 105)에서 실제 차이:

| | 업캐스트 복사 | `train_test_split` 복사 | 합계 |
|---|---:|---:|---:|
| float32 memmap | 12.18GB | 10.96GB | **≈ 23GB** |
| **float64 memmap** | 없음 | 10.96GB | **≈ 11GB** |

계산값 23.1GB와 실측 private 22.9GB가 맞아떨어져 **가설이 검증됐다.**

> **디스크를 아끼려던 선택이 RAM을 두 배로 쓰고 있었다.**
> 디스크는 6.09 → 12.18GB로 늘지만, 작업 디렉터리를 여유 있는 드라이브에 두면 그만이다.

dtype을 파일명에 박아 섞이지 않게 했다 — 이전 실행이 남긴 다른 dtype의 memmap을
덮어쓰면 크기가 어긋나 **조용히 깨지기** 때문이다.

```python
MATRIX_MEMMAP_NAME = {"float32": "X_f32.memmap", "float64": "X_f64.memmap"}
```

## 5. 남은 피크는 **고치지 않았다**

11GB 중 10.96GB가 `train_test_split`이다. `early_stopping='auto'`는 n > 10,000에서
켜지므로, sklearn이 **비닝 전에** 90%를 복사한다. 이건 memmap dtype과 무관하다.

`early_stopping=False`로 없앨 수 있다. 그런데 그러면 학습 데이터가 90% → 100%로
바뀌어 **다른 모델**이 된다.

여기서 미묘한 판단이 하나 있었다. 현 모델은 `n_iter_ = 250 == max_iter`라
**조기종료가 실제로 발동한 적이 없다.** 즉 끄더라도 학습 곡선은 안 바뀐다.

그래도 안 껐다.

> 발동한 적이 없다는 건 **지금까지의 데이터에서** 그랬다는 뜻이지,
> 앞으로도 그렇다는 보장이 아니다. 그리고 학습 데이터가 90% → 100%로 바뀌는 건
> 그 자체로 정본 등가를 깨는 변경이다.

이 경로의 목적은 **"같은 모델을 더 적은 메모리로"** 다. 목적을 벗어나는 최적화는
얻는 것(10.96GB)이 커도 하지 않았다. 대신 왜 안 했는지를 독스트링에 남겼다.

## 6. 부수 효과 — 작업 디렉터리가 자산이 됐다

의도하지 않았던 이득이 나왔다. `--work-dir`에 남은 parts와 memmap을 **재사용**하면
**DB 접속이 0인** 분석 경로가 생긴다. 재전개(약 10분)도 없다.

```bash

```

```bash

```

```bash
py scripts/analysis/station_breakdown_staged.py --work-dir DIR
```

### 특히 워크포워드가 이 경로 덕분에 가능해졌다

정본 `holdout_eval.evaluate_rolling_folds`는 **DataFrame을 받는다.** 현재 데이터량에서는
RAM에 못 올린다. 정책(확장창 · 폴드마다 재학습 · 같은 하이퍼파라미터)과 출력 구조를
맞춘 memmap 버전을 따로 만들었다.

폴드 간격도 다시 정했다. 정본은 테스트일마다 재학습이라 28일이면 **26폴드 · 약 7시간**이다.
간격을 3일로 열어 **8폴드 · 약 2.5시간**으로 잡았다 —
폴드끼리 학습 데이터가 대부분 겹치므로 하루 간격이 3배의 정보를 주지 않는다.

그리고 이 워크포워드가 없었다면 [케이스 1](CASE_01_model_bench.md)·[2](CASE_02_blend_weight.md)의
판정 규칙을 서빙 모델에 적용할 수 없었다.

## 7. 두 번 낭비하고 배운 것 — 예측을 덤프한다

세그먼트 분석을 하다가 같은 실수를 **두 번** 했다.
세그먼트를 새로 자를 때마다 홀드아웃을 **재적합**한 것이다(임계값 25분 · 충전소 32분).

원인이 둘이었다.

1. parts에 **식별자가 없어서** 세그먼트를 자를 수 없었다 → DB 재전개 약 10분
2. 예측값을 안 남겨서 다시 자를 때마다 적합부터 → 25분 · 32분

고친 방법은 단순하다. **test 예측을 parquet으로 덤프한다.**

```python
t[["stat_id", "chger_id", "created_at", "eta_minutes",
   "is_fast", "busi_id", "output_kw", "y", "proba"]].to_parquet(...)
```

2,977,654행이 **18.5MB**(zstd)이고, 그걸로 잔차 분석이 **6.8초**에 끝난다.
사업자별·출력별·시간대별 어떤 분해든 재적합 없이 몇 초다.

식별자를 parts에도 넣었다. **풀링 지표만으로는 병목을 못 찾기 때문**에,
세그먼트로 자를 수 있는 상태를 기본으로 두는 게 맞다.

## 8. 결과 — 그리고 반전

인프라는 완성됐다. 45일이 차도 학습이 돌고, 워크포워드 8폴드가 2.5시간에 끝나고,
세그먼트 분해가 몇 초다.

그런데 이 인프라로 얻은 가장 큰 결론이 이거였다.

> **재학습으로 지표가 오르지 않는다.**

8폴드 워크포워드에서 학습행이 **2.46M → 13.79M(5.6배)** 로 늘었는데
AUC와의 상관이 **−0.060**이었다. 5일 학습(0.9783)이 26일 학습(0.9756)보다 높았다.
구 모델을 같은 창에 태운 직접 대조도 AUC **+0.0002** · Brier −0.0002로 무승부다
(폴드 std 0.0038의 0.05배).

**재학습은 낡음 리셋(유지보수)이지 개선이 아니다.** 승격 근거로 쓰면 안 된다.

> 성능을 올리려고 만든 인프라가 아니라 **"성능이 안 오른다"를 증명할 수 있게 해준
> 인프라**였다. 이걸 모르면 매번 재학습하고 지표가 흔들리는 걸 개선으로 착각한다.

## 9. 정리

1. **제약이 늘어나는 방향인지 본다.** 21.5GB는 큰 머신으로 넘길 수 있지만,
   보존 정책이 45일이라 2.4배가 예정돼 있었다. 그래서 메모리에 비례하지 않는 경로를 골랐다.
2. **최적화 경로는 "같은 결과"부터 증명한다.** `_BinMapper`의 표본추출 때문에
   행 순서만 달라도 예측이 0.086 벌어진다. 등가 테스트가 없었으면 몰랐을 것이다.
3. **직관과 반대일 수 있으니 잰다.** float32가 디스크를 줄이는 대신 RAM을 두 배 썼다.
   원인은 라이브러리 내부의 dtype 검사였고, 계산값과 실측 private가 맞아떨어져 확인됐다.
4. **목적을 벗어나는 최적화는 하지 않는다.** `early_stopping`을 끄면 10.96GB를 아끼지만
   학습 데이터가 바뀐다. 안 한 이유를 코드에 남겼다.
5. **중간 산출물을 버리지 않는다.** work-dir 재사용으로 DB 접속 0인 분석 경로 3종이 생겼고,
   예측 덤프 18.5MB가 재적합 25분을 6.8초로 바꿨다.
6. **인프라의 가치는 성능 향상이 아닐 수 있다.** 이 경로가 준 가장 큰 결론은
   "재학습으로는 안 오른다"였고, 그건 **하지 않아도 될 일을 알려준 것**이다.
