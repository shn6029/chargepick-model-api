> 실제 수집기는 **원격 호스트의 Docker 컨테이너**에서 동작 중입니다.
> 로컬(`F:\dev\scheduler`)에서 prod DB에 직접 쓰지 마세요 — fetch 검증만 합니다.

## 0-A. 서버 용량 제약 — 실제 장애가 났던 부분 🔥

**ev-aws(<SERVER_IP>)는 vCPU 2개 / RAM 1,907MB 이고, 같은 인스턴스에서 MySQL(team_5)이
돌고 있습니다.** flask-app, parking-collector 도 같이 있습니다.

2026-07-31, `features` 컨테이너(pandas)를 10분 주기 전량 스냅샷과 함께 올렸다가
서버 전체가 마비됐습니다:

```
load average 63,  메모리 1,631/1,907MB,  컨테이너 Exited(137)
→ MySQL 쿼리 타임아웃, sshd 핸드셰이크 실패
→ HeidiSQL "handshake: reading initial communication packet" 오류
```

MySQL 이 죽은 게 아니라 **CPU 를 못 얻어 핸드셰이크를 못 끝낸 것**이었습니다.
`docker compose stop features snapshot` 으로 복구했습니다.

### 왜 복구가 오래 걸렸나 — 버스터블 인스턴스

Lightsail 은 **버스트 크레딧** 방식입니다.

```
Sustainable zone : CPU ≤ 20%   (베이스라인, 크레딧 유지)
Burstable zone   : CPU > 20%   (크레딧 소모)
크레딧 소진      : 강제 스로틀 → 부하를 없애도 한참 응답 불능
```

13:20~13:35 사이 CPU 70% 를 지속하다 크레딧이 바닥났습니다. 그래서 컨테이너를
멈춘 뒤에도 MySQL·sshd 가 살아나지 않았고, 결국 재부팅해야 했습니다.

**설계 목표는 "안 죽는 것"이 아니라 지속 CPU 20% 이하 유지입니다.**

### 규칙

- **pandas 워크로드를 이 서버에서 돌리지 마세요.** DB 서버 밖(PC 등)에서 실행합니다.
- 서버 밖에서 돌려도 **DB 쿼리 비용은 그대로 서버로 갑니다.** 쿼리를 가볍게 유지하세요.
- 전량 스냅샷(회당 25,433행)은 피처 빌드 부하를 약 15배로 키웁니다.
  10분 주기면 2시간 창에 약 30만행입니다. 현재 사양으로는 불가능합니다.
- `compute_features()` 는 충전기별 Python 루프라 **충전기 수에 비례**해 느려집니다.
  실측: 19K행/13K대 33초 → 32K행/25K대 193초.

### 인덱스 (2026-07-31 추가)

`ev_charger_status` 에 `created_at` 인덱스가 **없어서** 모든 시간범위 조회가
76만행 풀스캔이었습니다. 추가했습니다:

```sql
ALTER TABLE ev_charger_status ADD INDEX idx_created_at (created_at);
ALTER TABLE ev_charger_status ADD INDEX idx_charger_created (stat_id, chger_id, created_at);
```

기존 인덱스는 `stat_upd_dt` 기준이라(`idx_time`, `idx_stat_time`) 도움이 안 됐습니다.

### 쿼리 비용 실측 (765K행 기준)

| 쿼리 | 소요 |
|---|---|
| `load_status` 6h | 5.4초 |
| `load_anchors` horizon **7일** | 14.7초 |
| `load_anchors` horizon **1일** | **2.3초** ← 기본값 |

앵커 horizon 을 1일로 낮춘 것이 가장 큰 절감입니다. 360분 캡 때문에 모델 입력에는
차이가 거의 없습니다. **7일로 되돌리지 마세요.**

### 스냅샷을 다시 켜려면 (선행 조건)

1. `compute_features()` 벡터화 + 청크 처리
2. 또는 스냅샷 주기 완화(60분이면 부하 1/6, 대신 ±6분 라벨 커버 약 20%)
3. 또는 인스턴스 사양 상향(4GB+, 버스트 아닌 플랜)
4. 또는 피처 빌드 전용 별도 인스턴스

## 0. 배포 전 반드시 알아야 할 것 ⚠️

현재 원격에서 도는 이미지는 **파일이 `scripts/etl/` 로 옮겨지기 전**에 빌드된 구버전입니다.
그 사이 저장소의 `scripts/etl/run.py` 에는 필드 회전 버그가 있었고(2026-07-31 수정 완료),

**수정 전 코드로 배포하면 `ev_charger_status` 가 통째로 손상됩니다:**

```

chger_id <- statId   = "ME178137"
busi_id  <- chgerId  = "01"

배포 전 `scripts/etl/run.py` 의 `FIELDS` 순서가 `INSERT_SQL` 컬럼 순서와
일치하는지 눈으로 확인하세요.

```
INSERT_SQL: (stat_id, chger_id, busi_id, stat, stat_upd_dt, last_tsdt, last_tedt, now_tsdt)
FIELDS:     (statId,  chgerId,  busiId,  stat, statUpdDt,   lastTsdt,  lastTedt,  nowTsdt)

|---|---|---|

### ⚠️ `features` 는 반드시 서버에서 돌려야 합니다

서빙이 `ev_charger_features` 에 INNER JOIN 하고 60분 신선도를 요구하므로,
피처 생성이 멈추면 **60분 뒤 추천이 0건**이 됩니다.

로컬 PC 작업 스케줄러(`scripts/incremental_features.ps1`)는 임시방편이며,
**PC 를 끄면 멈춥니다.** 서버 배포 후에는 로컬 작업을 지우세요:

```bat
schtasks /Delete /TN "scheduler-incremental-features" /F
```

> 로컬에서 잠시 더 운영해야 한다면 `scripts/incremental_features_hidden.vbs` 로
> 등록하면 5분마다 콘솔 창이 뜨지 않습니다. 다만 PC 종료 문제는 그대로입니다.

**주기를 10분으로 잡은 근거**: 라벨이 `merge_asof(±6분)` 이므로 스냅샷 간격 `P` 에 대해
매칭 확률 ≈ `min(1, 12/P)`.

| 주기 | 일 적재량(≈) | ±6분 창 커버 |
|---|---|---|
| 10분 | 370만행 | ≈100% ← 채택 |
| 15분 | 240만행 | ≈80% |
| 30분 | 122만행 | ≈40% |
| 60분 | 61만행 | ≈20% |

30분으로는 Phase 3 목표(stat=3 행의 h30 매칭률 9.1% → 수십 %)를 못 채웁니다.

## 4. 스키마 변경

`run_status_snapshot.py` 최초 실행 시 아래를 **자동 추가**합니다. 미리 적용하려면:

```sql
-- 수집 경로 구분. 기존 행과 run.py 의 INSERT 는 DEFAULT 로 'delta' 가 들어간다.
ALTER TABLE ev_charger_status
    ADD COLUMN source VARCHAR(10) NOT NULL DEFAULT 'delta'
    COMMENT '수집 경로: delta=getChargerStatus 변경분, snapshot=getChargerInfo 전량';

-- 실제 관측(폴링) 시각. created_at(DB insert 시각)과 다르다:
-- 3페이지 fetch + 배치 insert 에 수십 초가 걸려 배치 내 행마다 created_at 이 흩어진다.
ALTER TABLE ev_charger_status
    ADD COLUMN observed_at DATETIME NULL
    COMMENT '실제 관측(폴링) 시각. NULL 이면 created_at 사용';

ALTER TABLE ev_charger_status
    ADD COLUMN snapshot_batch_id VARCHAR(36) NULL
    COMMENT '스냅샷 배치 식별자';
```

그리고 배치 이력 테이블 `ev_status_snapshot_batch` 가 생성됩니다.
**부분 스냅샷(전 페이지를 못 받은 배치)을 학습에서 걸러내려면 이 표가 필요합니다.**

```sql
-- 최근 배치 상태
SELECT batch_id, observed_at, expected_count, fetched_count, saved_count,
       is_complete, error
FROM ev_status_snapshot_batch
ORDER BY observed_at DESC LIMIT 10;

-- 미완료 배치가 있으면 그 batch_id 의 행은 학습에서 제외
SELECT batch_id FROM ev_status_snapshot_batch WHERE is_complete = 0;
```

### 미결정: 서빙 신선도 기준 (P1.3)

현재 서빙은 `created_at` 기준으로 60분 신선도를 판단합니다
(`config.VERY_STALE_EXCLUDE_MIN`). `observed_at` 기준으로 바꾸는 편이 의미상 맞지만,
**10분 주기 스냅샷이 들어가면 모든 충전기가 10분마다 새 행을 얻으므로
"오래 상태가 안 변한 정상 충전기가 후보에서 빠지는" 증상 자체는 해소됩니다.**
서빙 semantics 변경은 추천 결과를 바꾸므로 스냅샷 투입 후 별도로 판단하세요.

## 6. 투입 3~7일 후 — 편향 재측정

스냅샷이 쌓인 뒤 stat별 h30 매칭률을 다시 재고, 두 자릿수 → 수십 %로 올라왔는지 봅니다.

```sql
SELECT s.stat AS current_stat, COUNT(*) AS rows_cnt,
       ROUND(100*SUM(EXISTS(
         SELECT 1 FROM ev_charger_status n
         WHERE n.stat_id=s.stat_id AND n.chger_id=s.chger_id
           AND n.created_at BETWEEN DATE_ADD(s.created_at, INTERVAL 24 MINUTE)
                               AND DATE_ADD(s.created_at, INTERVAL 36 MINUTE)
       ))/COUNT(*),1) AS h30_match_pct
FROM ev_charger_status s
WHERE s.created_at BETWEEN '<시작>' AND '<종료>'
GROUP BY s.stat ORDER BY rows_cnt DESC;
```

**투입 전 기준선 (2026-07-31 실측)**

| 현재 stat | h30 매칭률 |
|---|---|
| 2 (대기) | 82.8% |
| 3 (충전중) | **9.1%** |
| 1 (통신이상) | 9.6% |
| 4 (운영중지) | 0% |

매칭률이 회복되면 그때 재학습을 판단합니다
(승격 기준은 `recommend_api/artifacts/EVALUATION_horizon_hgb_0727.md`).
